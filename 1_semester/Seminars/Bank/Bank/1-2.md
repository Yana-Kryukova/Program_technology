## 3. Блок SRP (15 мин)

**Показать на экране:**

```csharp
public class BankAccount
{
    static private int s_accountNuberSeed = 1000000000;
    public string Number { get; }
    public string Owner { get; private set; }
    public decimal Balance { get { /* цикл по транзакциям */ } }

    public BankAccount(string name, decimal initialBalance, decimal minimumBalance) { /* номер, owner, minimumBalance, депозит */ }
    public void MakeDeposit(...) { ... }
    public void MakeWithdrawal(...) { ... }
    protected virtual Transaction? CheckWithdrawalLimit(bool isOverdrawn) { ... }
    public string GetAccountHistory() { /* StringBuilder, форматирование */ }
    public virtual void PerformMonthAndTransactions() { }
    public override string ToString() { ... }
}
```

**Вопрос группам:** сколько ответственностей у класса? Назовите зоны изменения.

**Ожидаемые ответы (для сверки):**

| № | Суть нарушения | Риск / последствие |
|---|---|---|
| 1 | Один класс отвечает сразу за идентификацию счёта (`Number`, `Owner`), хранение и подсчёт баланса, правила овердрафта (`CheckWithdrawalLimit`), месячные операции и формирование отчёта | Любое изменение любой из зон заставляет править один и тот же класс; он растёт и становится хрупким |
| 2 | Смешаны доменная логика (выборка транзакций, подсчёт баланса) и представление (форматирование текстового отчёта) | Нельзя добавить JSON/CSV-отчёт без правки класса счёта; логика и формат склеены |
| 3 | Генерация номера «вшита» в счёт и является глобальным состоянием | Номера не воспроизводимы в тестах, нельзя заменить схему нумерации (GUID, префиксы) |

**Обсудить:** «А если завтра надо отчёт в JSON? А если номера должны быть GUID? Кто и что будет менять?» — это и есть проверка риска.

## 4. Блок OCP (15 мин)

**Показать на экране:**

```csharp
public BankAccount(string name, decimal initialBalance, decimal minimumBalance) { ... }
protected virtual Transaction? CheckWithdrawalLimit(bool isOverdrawn) { ... }

public class LineOfCreditAccount : BankAccount
{
    public LineOfCreditAccount(string name, decimal initial, decimal creditLimit)
        : base(name, initial, -creditLimit) { }
    public override void PerformMonthAndTransactions()
    {
        if (Balance < 0) { decimal interest = -Balance * 0.07m; /* ... */ }
    }
    protected override Transaction? CheckWithdrawalLimit(bool isOverdrawn)
        => isOverdrawn ? new Transaction(-20, DateTime.UtcNow, "apply overdraft") : default;
}

public class InterestEarningAccount : BankAccount
{
    public override void PerformMonthAndTransactions()
    {
        if (Balance > 500m) { decimal interest = Balance * 0.02m; /* ... */ }
    }
}
```

**Вопрос группам:** что пришлось изменить в **базовом** классе, чтобы появился кредитный счёт? Что будет, если завтра нужен «Студенческий счёт» с другими ставками?

**Ожидаемые ответы:**

| № | Суть нарушения | Риск / последствие |
|---|---|---|
| 4 | Чтобы добавить линию кредита, пришлось менять уже работающий базовый класс (добавлен `_minimumBalance`, изменён `MakeWithdrawal`, появился новый `CheckWithdrawalLimit`) | Расширение через модификацию; следующий тип снова потребует правок базы — риск сломать работающее |
| 5 | Правила и их параметры (ставка `0.02`, порог `500`, ставка долга `0.07`, комиссия `-20`) «зашиты» в код наследников | Изменение ставки или порога требует правки и перекомпиляции; нельзя настроить счёт без программиста |

## 5. Блок LSP (15 мин)

**Показать на экране рядом:**

```csharp
// базовый:
protected virtual Transaction? CheckWithdrawalLimit(bool isOverdrawn)
{
    if (isOverdrawn) throw new InvalidOperationException("Not sufficient funds");
    return default;
}

// наследник:
protected override Transaction? CheckWithdrawalLimit(bool isOverdrawn)
    => isOverdrawn ? new Transaction(-20, DateTime.UtcNow, "apply overdraft") : default;
```

И отдельно:

```csharp
public class GiftCartAccount : BankAccount { /* только PerformMonthAndTransactions и ToString */ }
```

**Вопрос:** базовый метод **бросает исключение**, переопределённый — **возвращает транзакцию**. Что это значит для клиента, который держит `BankAccount` и вызывает `MakeWithdrawal`?

**Ожидаемые ответы:**

| № | Суть нарушения | Риск / последствие |
|---|---|---|
| 6 | Базовый метод и переопределённый имеют **разный контракт**: один сигнализирует об ошибке исключением, второй — нормальным возвратом (добавляет комиссию). Подтип ведёт себя не так, как обещает родитель | Клиент через `BankAccount` не может полагаться на поведение; нельзя писать общий код без проверок `is LineOfCreditAccount` — теряется смысл полиморфизма |
| 7 | Подарочная карта «только погашается», но наследует `MakeWithdrawal` и всю модель счёта. Часть унаследованного поведения ей не свойственна | Наследование ради переиспользования, а не «является»; клиент может снять с подарочной карты больше, чем задумано бизнесом — дыра в правилах |

| № | Суть нарушения | Риск / последствие |
|---|---|---|

## 7. Переход к этапу 2. Проектирование (25 мин)

**Постановка:** «Мы нашли 10 нарушений. Теперь — что с этим делать. Задача: чтобы новый тип счёта добавлялся без правки существующих классов».

**Действие 1 — «вывести абстракции» (10 мин, работа в группах).**
Раздать по одному нарушению каждой группе и попросить сформулировать: **какая абстракция убирает нарушение?**

| Нарушение | Абстракция |
|---|---|
| `DateTime.UtcNow` | `IClock` |
| `s_accountNuberSeed` | `IAccountNumberGenerator` |
| разные контракты `CheckWithdrawalLimit` | `IWithdrawalPolicy` + `WithdrawalDecision` |
| правила конца месяца «зашиты» в наследников | `IMonthEndRule` + `List<IMonthEndRule>` |
| формирование отчёта в счёте | `IStatementFormatter` |
| «толстый» класс | `IAccountOperations`, `IAccountStatement` |

**Действие 2 — собрать схему (10 мин).**
Группы рисуют на листах А3, как «тонкое ядро» `BankAccount` принимает зависимости. Затем преподаватель сводит на доске:

```
IClock ──────────────┐
IAccountNumberGenerator ─┤
IWithdrawalPolicy ────┤──► BankAccount ──► List<Transaction>
List<IMonthEndRule> ──┘        │
                               ├─ реализует IAccountOperations
                               └─ реализует IAccountStatement
IStatementFormatter ◄── читает Transactions
AccountFactory ── собирает счёт из политик и правил (пресеты типов)
```

**Действие 3 — проговорить решения (5 мин):**
- «Магические числа» → параметры конструкторов правил.
- `DateTime.UtcNow` → `IClock`.
- Разный контракт снятия → `WithdrawalDecision` (Allow / AllowWithFee / Reject).
- Отчёт → отдельный форматтер.
- Новый тип счёта → новый пресет в фабрике, без правок существующей логики.

### Абстракция 1. `IClock` — закрывает нарушение №9 (DIP)

**Что было:**

```csharp
// в конструкторе BankAccount:
MakeDeposit(initialBalance, DateTime.UtcNow, "Initial balance");

// в наследниках:
MakeWithdrawal(interest, DateTime.UtcNow, "Charge monthly interest");
```

**Абстракция:**

```csharp
public interface IClock { DateTime Now { get; } }
public sealed class SystemClock : IClock { public DateTime Now => DateTime.Now; }
```

**Механизм — как именно решает (это и есть ответ на вопрос группы):**

1. **Инверсия зависимости.** `BankAccount` перестаёт *сам* обращаться к статическому `DateTime.UtcNow` (глобальный источник, который нельзя подменить) и начинает *принимать* время через конструктор. Зависимость «счёт → системные часы» меняет направление: теперь счёт зависит от абстракции `IClock`, а конкретная реализация подставляется снаружи.
2. **Точка подмены.** В тесте создаётся `FrozenClock(fixedDate)`, и весь сценарий «конец месяца» идёт с одной и той же датой. Раньше это было невозможно: `DateTime.UtcNow` — статическое свойство, его не подменить ни наследованием, ни DI.
3. **Детерминизм транзакций.** Все транзакции получают дату из одного источника, поэтому в тесте можно проверить не только суммы, но и `Transaction.Date` — а значит, проверить, что проценты начислены именно «на конец месяца», а не «когда запустили тест».
4. **Границы дат становятся тестируемыми.** Можно прогнать правило процентов на 28/29 февраля, на границе месяца, «в полночь» — то, что с реальными часами тестировать больно.

**Что стало у клиента:**

```csharp
// было: BankAccount сам знает про время
new BankAccount("Yana", 1000);

// стало: время — внешняя зависимость
new BankAccount("Yana", 1000, clock: new SystemClock(), ...);
// в тесте:
new BankAccount("Yana", 1000, clock: new FrozenClock(new DateTime(2025, 1, 31)), ...);
```

**Что теперь тестируется:** `PerformMonthEndTransactions` на фиксированной дате; корректность `Transaction.Date`; граничные даты.

**Цена:** ещё один параметр в конструкторе; кто-то должен создавать `SystemClock` (это делает фабрика / точка входа).

### Абстракция 2. `IAccountNumberGenerator` — закрывает нарушение №3 (SRP)

**Что было:**

```csharp
static private int s_accountNuberSeed = 1000000000;

public BankAccount(...)
{
    Number = s_accountNuberSeed.ToString();
    s_accountNuberSeed++;      // глобальное состояние, меняется каждым new
}
```

**Абстракция:**

```csharp
public interface IAccountNumberGenerator { string Next(); }

public sealed class SequentialAccountNumberGenerator : IAccountNumberGenerator
{
    private int _seed;
    public SequentialAccountNumberGenerator(int seed = 1234567890) => _seed = seed;
    public string Next() => (_seed++).ToString();
}
```

**Механизм — как именно решает:**

1. **Убирает глобальное состояние из домена.** `s_accountNuberSeed` был `static` — один на весь процесс. Поэтому номер зависел от порядка создания счетов **во всём приложении**: тест, создавший счёт первым, сдвигал нумерацию для всех последующих тестов. Теперь состояние генератора живёт в его экземпляре и не протекает между тестами.
2. **Делает номер воспроизводимым.** `new SequentialAccountNumberGenerator(seed: 100)` в каждом тесте даёт предсказуемый номер. Раньше номер зависел от «сколько счетов уже успели создать» — тест на `Number` был либо хрупким, либо его просто не писали.
3. **Разделяет две ответственности.** Генерация номера — не дело счёта. Счёт хранит `Number` (это его данные), но *как* номер получился — не его забота. Теперь класс счёта не меняется, если завтра нужны GUID-номера или префиксы.
4. **Даёт точку расширения.** Нужна схема «префикс + год + счётчик» — добавляется новый класс-реализация, `BankAccount` не трогаем.

**Что стало:**

```csharp
// было:
new BankAccount("Yana", 1000);              // номер = 1000000000, 1000000001, ...

// стало:
new BankAccount("Yana", 1000, numbers: new SequentialAccountNumberGenerator(seed: 100));
// в тесте:
new BankAccount("Yana", 1000, numbers: new SequentialAccountNumberGenerator(seed: 42));
// → Number == "42", не зависит от других тестов
```

**Что теперь тестируется:** формат номера; воспроизводимость; независимость тестов друг от друга; замена схемы нумерации.

**Цена:** генератор нужно передавать при каждом создании (закроет фабрика).

### Абстракция 3. `IStatementFormatter` — закрывает нарушение №2 (SRP)

**Что было:**

```csharp
public string GetAccountHistory()
{
    var report = new StringBuilder();
    decimal balance = 0;
    report.AppendLine("Data\t\tAmount\tBalance\tNote");
    foreach (var item in _allTransactions)
    {
        balance += item.Amount;
        report.AppendLine($"{item.Date.ToShortDateString()}\t{item.Amount}\t{balance}\t{item.Note}");
    }
    return report.ToString();
}
```

**Абстракция:**

```csharp
public interface IStatementFormatter { string Format(IEnumerable<Transaction> transactions); }
public sealed class TextStatementFormatter : IStatementFormatter { /* StringBuilder */ }
```

**Механизм — как именно решает:**

1. **Разделяет домен и представление.** Выборка транзакций и подсчёт баланса — доменная логика. Форматирование в `Date\tAmount\tBalance\tNote` — представление. Сейчас они в одном методе, поэтому:
   - «добавить CSV» = править доменный класс;
   - «поправить домен» = риск сломать формат отчёта.
   После выноса счёт отдаёт **данные** (`Transactions`), а форматтер — **строку**.
2. **Открывает формат для расширения (в связке с OCP).** Новый формат = новый класс (`JsonStatementFormatter`, `CsvStatementFormatter`), `BankAccount` не меняется. Раньше требовалась правка `GetAccountHistory` — то есть модификация домена ради представления.
3. **Делает отчёт тестируемым отдельно.** Тест форматтера не создаёт счёт и транзакции через `MakeDeposit` — он подаёт список транзакций и сверяет строку. Домен и формат тестируются независимо.
4. **Позволяет выбрать формат в момент вывода.** Один и тот же счёт можно отрисовать текстом, JSON-ом, в UI — форматтер выбирается в точке использования.

**Что стало у клиента:**

```csharp
// было: account.GetAccountHistory()
// стало:
var formatter = new TextStatementFormatter();
Console.WriteLine(formatter.Format(account.Transactions));
```

**Что теперь тестируется:** отдельно — расчёт баланса и выборка; отдельно — точный формат строки.

**Цена:** клиенту нужно знать про форматтер. Это не «лишнее» — это явное разделение ролей.

### Абстракция 4. `IAccountOperations` + `IAccountStatement` — закрывает нарушение №8 (ISP)

**Что было:** ни одного интерфейса; клиенту, которому нужен только отчёт, приходится получать весь `BankAccount` с депозитом, снятием, месячными операциями.

**Абстракция:**

```csharp
public interface IAccountOperations
{
    decimal Balance { get; }
    void Deposit(decimal amount, DateTime date, string note);
    void Withdraw(decimal amount, DateTime date, string note);
}

public interface IAccountStatement
{
    IReadOnlyList<Transaction> Transactions { get; }
}
```

**Механизм — как именно решает:**

1. **Узкий контракт для клиента.** Клиент-отчётность зависит от `IAccountStatement` — и *физически не может* вызвать `Withdraw`. Клиент-кассир зависит от `IAccountOperations` — и не видит историю транзакций напрямую. Оба реализуются одним `BankAccount`, но зависят от разного среза поведения.
2. **Убирает «толстую» зависимость.** Раньше любое изменение `BankAccount` (например, добавление метода `Transfer`) задевало всех клиентов, даже тех, кто никогда не переводит. Теперь клиент зависит только от своего интерфейса — изменение «не его» части его не касается.
3. **Разблокирует подмену в тестах.** Для теста форматтера достаточно фейка `IAccountStatement` с тремя транзакциями — не нужен живой счёт. Для теста банкомата — фейк `IAccountOperations`. Раньше тест тянул весь объект.
4. **Помогает проектировать «снаружи внутрь».** Сначала решаем, какие операции нужны клиентам (депозит / снятие / история / месячные операции), потом раскладываем по интерфейсам — вместо «сделаем класс, а клиенты разберутся».

**Что стало у клиента:**

```csharp
// клиент-отчётность:
void PrintReport(IAccountStatement st) => Console.WriteLine(formatter.Format(st.Transactions));

// клиент-кассир:
void CashDesk(IAccountOperations ops) { ops.Deposit(100, clock.Now, "cash in"); }

// сам счёт по-прежнему один:
BankAccount account = ...;   // реализует оба интерфейса
```

**Что теперь тестируется:** клиенты тестируются на фейках интерфейсов, без создания настоящего счёта; отсутствие лишних зависимостей проверяется по сигнатурам.

**Цена:** одна абстракция — два интерфейса; нужно решить, где проходит граница среза (в нашем случае — операции vs. отчёт).

### Абстракция 5. `IWithdrawalPolicy` + `WithdrawalDecision` — закрывает нарушения №6 (LSP) и №10 (DIP)

> Это **самая важная** карточка этапа: она чинит LSP и DIP одним ходом и одновременно решает, как жить без `protected virtual CheckWithdrawalLimit`.

**Что было:**

```csharp
// база:
protected virtual Transaction? CheckWithdrawalLimit(bool isOverdrawn)
{
    if (isOverdrawn) throw new InvalidOperationException("Not sufficient funds");
    return default;
}

// наследник (линия кредита):
protected override Transaction? CheckWithdrawalLimit(bool isOverdrawn)
    => isOverdrawn ? new Transaction(-20, DateTime.UtcNow, "apply overdraft") : default;
```

**Абстракция:**

```csharp
public sealed record WithdrawalDecision(bool IsAllowed, decimal Fee, string? RejectionReason)
{
    public static WithdrawalDecision Allow()                => new(true, 0m, null);
    public static WithdrawalDecision AllowWithFee(decimal f) => new(true, f, null);
    public static WithdrawalDecision Reject(string r)       => new(false, 0m, r);
}

public interface IWithdrawalPolicy
{
    WithdrawalDecision Evaluate(decimal currentBalance, decimal amount, decimal minimumBalance);
}
```

**Механизм — как именно решает:**

1. **Один контракт на все политики.** Раньше было **два** разных контракта: база «кидает исключение», наследник «возвращает транзакцию». Клиент не мог написать `try { account.MakeWithdrawal(...) }`, не зная, от какого класса пришёл счёт. Теперь все политики возвращают `WithdrawalDecision` одного типа: `IsAllowed`, `Fee`, `RejectionReason`. Любой клиент обрабатывает результат единообразно.
2. **LSP становится проверяемым.** Подстановка `OverdraftFeeWithdrawalPolicy` вместо `StrictWithdrawalPolicy` не меняет **тип** результата и не меняет правила игры: клиент всегда смотрит `decision.IsAllowed`, всегда видит `decision.Fee`, всегда получает `RejectionReason` при отказе. Подтип больше не «ведёт себя иначе, чем обещает родитель» — он просто другой экземпляр той же абстракции.
3. **DIP: правило овердрафта — не внутри класса.** Решение о допустимости снятия принимает не `BankAccount` (через `throw` в `CheckWithdrawalLimit`), а внедрённая политика. Меняем правило — передаём другой экземпляр; `BankAccount` не правим.
4. **Комиссия — часть решения, а не побочный эффект наследника.** Раньше «комиссия» появлялась только у `LineOfCreditAccount` через переопределение `CheckWithdrawalLimit`. Теперь любая политика может вернуть `AllowWithFee(fee)`, и `BankAccount` одинаково добавляет транзакцию-комиссию. Это снимает привязку «комиссия = кредитный счёт».
5. **Исчезает `protected virtual` как точка расширения.** Метод-хук `CheckWithdrawalLimit` был нужен только потому, что правила нельзя было вынести. Теперь такой метод не нужен: `BankAccount` делегирует в политику. Это и убирает нарушение OCP из строки №4 в части «правило снятия».

**Что стало у клиента:**

```csharp
// было: клиент не знал, ждать ли исключения или транзакции
try { account.MakeWithdrawal(amount, date, note); } catch (InvalidOperationException) { ... }

// стало: единый исход
var decision = policy.Evaluate(balance, amount, minimumBalance);
if (!decision.IsAllowed) { /* decision.RejectionReason */ }
// а внутри BankAccount:
var d = _withdrawalPolicy.Evaluate(Balance, amount, MinimumBalance);
if (!d.IsAllowed) throw new InvalidOperationException(d.RejectionReason);
if (d.Fee > 0) _transactions.Add(new Transaction(-d.Fee, date, "Apply overdraft fee"));
```

**Что теперь тестируется:** политика — изолированно, как чистая функция `(balance, amount, min) → decision`; `BankAccount` — с фейковой политикой, без овердрафт-логики; больше не нужно проверять `is LineOfCreditAccount`.

**Цена:** вводится DTO `WithdrawalDecision`; `BankAccount` остаётся единственным местом, где `IsAllowed == false` превращается в исключение (это осознанное решение, а не протечка).

### Абстракция 6. `IMonthEndRule` (+ список) — закрывает нарушения №4, №5 (OCP) и часть №1 (SRP)

**Что было:**

```csharp
// InterestEarningAccount:
public override void PerformMonthAndTransactions()
{
    if (Balance > 500m) { decimal interest = Balance * 0.02m; MakeDeposit(interest, DateTime.UtcNow, "Apply month interest"); }
}

// LineOfCreditAccount:
public override void PerformMonthAndTransactions()
{
    if (Balance < 0) { decimal interest = -Balance * 0.07m; MakeWithdrawal(interest, DateTime.UtcNow, "Charge monthly interest"); }
}

// GiftCartAccount:
public override void PerformMonthAndTransactions()
{
    if (_monthlyDeposit != 0) MakeDeposit(_monthlyDeposit, DateTime.UtcNow, "Add monthly deposit");
}
```

**Абстракция:**

```csharp
public interface IMonthEndRule { void Apply(IAccountOperations account, DateTime asOf); }

public sealed class InterestOnPositiveBalanceRule : IMonthEndRule
{
    private readonly decimal _rate;
    private readonly decimal _threshold;
    public InterestOnPositiveBalanceRule(decimal rate, decimal threshold) { _rate = rate; _threshold = threshold; }
    public void Apply(IAccountOperations account, DateTime asOf)
    {
        if (account.Balance > _threshold)
            account.Deposit(account.Balance * _rate, asOf, "apply monthly interest");
    }
}
```

**Механизм — как именно решает:**

1. **Заменяет переопределение на композицию списка.** Каждый наследник переопределял `PerformMonthAndTransactions` и «вшивал» своё правило. Теперь `BankAccount` содержит `List<IMonthEndRule>` и в `PerformMonthEndTransactions` просто прогоняет его. Счёт не знает, *какие* правила у него есть, — он знает только, что их можно применить.
2. **Убирает модификацию базового класса при добавлении типа (OCP).** Раньше новый тип счёта = новый наследник + правка цепочки в `Program`. Теперь новый тип = **новый набор правил**, переданный в конструктор. Ни `BankAccount`, ни существующие правила не меняются.
3. **Выносит «магические числа» в параметры (OCP, №5).** Ставка `0.02`, порог `500`, ставка долга `0.07` — теперь аргументы конструктора правила. Изменение ставки = другая конфигурация в фабрике, а не правка класса. Это же делает возможным «студенческий счёт» со ставкой `0.025` и порогом `300` на этапе 4 — без нового класса.
4. **Разделяет правила между собой (SRP).** Раньше `PerformMonthAndTransactions` в каждом наследнике был «комбайном» с условием и формулой. Теперь одно правило — один класс с одной формулой. Правило процентов на положительный баланс не знает про правило долга; их можно включать/выключать независимо.
5. **Позволяет применять несколько правил к одному счёту.** Линия кредита = «проценты на долг». Но если бизнес завтра скажет «ещё и сервисная комиссия раз в месяц» — это второе правило в том же списке, без изменения первого. Раньше пришлось бы переписывать `PerformMonthAndTransactions` наследника.
6. **Согласует сигнатуру с узким интерфейсом.** `Apply(IAccountOperations account, ...)` — правило работает только с операциями (депозит/снятие/баланс), но не с отчётом. Это перекликается с ISP из карточки 4 и не даёт правилу «залезть» в чужие обязанности.

**Что стало:**

```csharp
// было: 3 наследника с override
// стало: 1 BankAccount + наборы правил в фабрике
new BankAccount(..., monthEndRules: new IMonthEndRule[]
{
    new InterestOnPositiveBalanceRule(rate: 0.02m, threshold: 500m)
});
// и всё: PerformMonthEndTransactions — просто цикл по списку
```

**Что теперь тестируется:** каждое правило — отдельно, как чистая функция `(account-фейк, дата) → изменение транзакций`; `BankAccount` — с фейковым правилом; комбинации правил — без создания наследников.

**Цена:** правила становятся объектами, которые надо собирать; при большом числе правил фабрика растёт (её и выносим в отдельную точку — см. Действие 3).

### Сводка Действия 1 (эталон для доски)

| № | Абстракция | Закрывает нарушение | Механизм в одну строку |
|---|---|---|---|
| 1 | `IClock` | №9 (DIP) | время — параметр, а не `DateTime.UtcNow` → детерминизм в тестах |
| 2 | `IAccountNumberGenerator` | №3 (SRP) | убирает `static`-состояние и генерацию из счёта → воспроизводимые номера |
| 3 | `IStatementFormatter` | №2 (SRP) | домен отдаёт данные, форматтер — строку → JSON/CSV без правки счёта |
| 4 | `IAccountOperations` / `IAccountStatement` | №8 (ISP) | клиент зависит от среза, а не от «толстого» класса → фейки в тестах |
| 5 | `IWithdrawalPolicy` + `WithdrawalDecision` | №6 (LSP), №10 (DIP) | один контракт вместо «исключение vs возврат» → подстановка без `is`-проверок |
| 6 | `IMonthEndRule` + список | №4, №5 (OCP), часть №1 (SRP) | правило — объект в списке, а не `override` в наследнике → новый тип = новый набор правил |
| 7 | `AccountFactory` (см. Действие 3) | №4 (OCP) | сборка счёта из политик и правил в одном месте → новый тип = новый пресет |

## Действие 2. Сборка схемы зависимостей (20 мин)

**Задача:** нарисовать, **кто на кого ссылается** после введения абстракций. Схема должна отвечать на три вопроса: (а) от чего зависит `BankAccount`; (б) что зависит от `BankAccount`; (в) где создаётся всё это.

### Шаг 2.1. Раздать группам листы А3 и маркеры (3 мин)

**Вопросы, на которые каждая группа отвечает прежде, чем рисовать:**

1. Кто **внедряется** в `BankAccount`? (стрелка «в»)
2. Что `BankAccount` **реализует**? (стрелка «реализует»)
3. Что `BankAccount` **хранит**? (стрелка «хранит», не путать с «зависит»)
4. Кто **читает** транзакции счёта? (стрелка «читает»)
5. Кто **создаёт и собирает** счёт? (стрелка «создаёт»)

### Шаг 2.2. Группы рисуют (10 мин)

**Эталонный результат:**

```
IClock ───────────────┐
IAccountNumberGenerator ─┤
IWithdrawalPolicy ─────┤──► BankAccount ──► List<Transaction>
List<IMonthEndRule> ───┘        │
                                ├─ реализует IAccountOperations
                                └─ реализует IAccountStatement
IStatementFormatter ◄── читает Transactions
AccountFactory ── создаёт ──► BankAccount (внедряет все зависимости)
```

### Шаг 2.3. Что преподаватель проверяет и какие ошибки ловит (7 мин)

Пройти по каждой схеме и явно указать на типичные ошибки — они повторяются почти всегда:

| Типичная ошибка в схеме | Почему неверно | Как чинить |
|---|---|---|
| Стрелка `AccountFactory → BankAccount` нарисована как «зависимость» счёта от фабрики | Направление перевёрнуто: счёт **не знает** про фабрику, фабрика **создаёт** счёт. Если счёт начнёт зависеть от фабрики — вернётся DIP-нарушение | Стрелку «создаёт» рисовать отдельным стилем (пунктир), не путать с «внедряется» |
| `BankAccount` зависит от **конкретной** `StrictWithdrawalPolicy` | Это то же нарушение DIP, что и было: зависимость от реализации | Стрелка только к `IWithdrawalPolicy`; конкретика — только в фабрике |
| `List<IMonthEndRule>` нарисован как один блок «правило» | Теряется главный смысл: их **много**, список открыт для расширения | Рисовать как коллекцию / множественную стрелку |
| `IStatementFormatter` повешен как зависимость `BankAccount` | Счёт не должен знать про форматтер — иначе SRP снова смешан (счёт → представление) | Стрелка «читает `Transactions`», а не «внедряется в счёт» |
| `IAccountOperations` / `IAccountStatement` нарисованы как **зависимости** счёта | На самом деле счёт их **реализует**; зависимости — это `IClock` и т.п. | Разделять стили: «внедряется» vs «реализует» |
| Стрелка `BankAccount → Transaction` нарисована как «зависит» | `Transaction` — это данные, которые счёт **хранит**; счёт зависит от неё ровно так же, как от `decimal` | Пометить «хранит», не трактовать как архитектурную зависимость |
| Нет `AccountFactory` вообще | Тогда непонятно, кто передаёт `SystemClock`, `SequentialAccountNumberGenerator`, политики и правила — а без этого этап 3 не собрать | Фабрика — обязательный блок схемы |

### Шаг 2.4. Свести к одной схеме на доске (по ходу 2.3)

**Ключевая фраза, которую нужно проговорить группам:**

> «Все стрелки в `BankAccount` идут **от абстракций**. Конкретика (`SystemClock`, `Sequential...`, `Strict...`, `Interest...`) живёт **только в фабрике**. Если у вас на схеме конкретный класс внедряется в счёт напрямую — вы всё ещё нарушаете DIP.»

Это и есть проверка схемы на соответствие этапу 1: если какая-то стрелка идёт от конкретики к счёту — соответствующее нарушение из таблицы не закрыто.

## Действие 3. Фиксация решений и роль фабрики (15 мин)

**Задача:** превратить абстракции и схему в **список конкретных решений**, которые на этапе 3 станут кодом. Это не пересказ Действия 1, а «как именно мы это соберём».

### Шаг 3.1. Таблица решений (7 мин)

Преподаватель ведёт заполнение таблицы, группы дописывают в свои конспекты. Колонка «Что делаем» — это **императив**, колонка «Почему» — ссылка на нарушение.

| Проблема из этапа 1 | Что делаем | Почему (нарушение) |
|---|---|---|
| «Магические числа» (`0.02`, `500`, `0.07`, `-20`) | Выносим в **параметры конструкторов** правил и политик (`InterestOnPositiveBalanceRule(rate, threshold)`, `OverdraftFeeWithdrawalPolicy(fee)`) | №5 (OCP): изменение ставки ≠ правка класса |
| `DateTime.UtcNow` | Внедряем `IClock`; в конструкторе счёта — `clock.Now` | №9 (DIP) |
| Разные контракты `CheckWithdrawalLimit` | Вводим `IWithdrawalPolicy` + `WithdrawalDecision`; удаляем `protected virtual` хук | №6 (LSP), №10 (DIP) |
| Отчёт внутри счёта | Выносим `IStatementFormatter`; счёт отдаёт `Transactions` | №2 (SRP) |
| `static s_accountNuberSeed` | Внедряем `IAccountNumberGenerator` | №3 (SRP) |
| «Толстый» класс | Реализуем `IAccountOperations` + `IAccountStatement`; клиенты зависят от срезов | №8 (ISP) |
| Правила конца месяца в наследниках | `List<IMonthEndRule>` + правила-объекты; удаляем `override PerformMonth...` у наследников | №4, №5 (OCP), часть №1 (SRP) |
| **Как всё это собрать** | `AccountFactory` — единственное место, где создаются конкретные `SystemClock`, `Sequential...`, политики и правила по пресетам типов | №4 (OCP): новый тип = новый пресет, без правки существующей логики |

### Шаг 3.2. Почему именно фабрика, а не «наследники» и не DI-контейнер (8 мин)

Это вопрос, который группы почти всегда задают: «а можно было оставить наследников?», «а зачем фабрика, если есть DI?». Ответы — часть этапа:

1. **Наследники `InterestEarningAccount` / `LineOfCreditAccount` / `GiftCartAccount` больше не нужны.** Их различия сводятся к **набору параметров** (ставка, порог, комиссия, лимит, месячное пополнение) + **набору правил**. Наследование ради поведения заменяется композицией. Оставлять наследников = оставлять OCP-нарушение №4.
2. **Фабрика — это точка, где конкретика встречается с абстракцией.** Всё, что нарушало DIP (конкретные часы, генератор, политики), теперь создаётся **в одном месте**. `BankAccount` знает только интерфейсы.
3. **Пресеты типов счетов читаются как постановка задачи.** `CreateStudentAccount(...)` на этапе 4 — это 6 строк конфигурации, а не новый класс. Это и есть демонстрация OCP, которую ждёт этап 4.
4. **DI-контейнер здесь избыточен.** В учебном примере зависимостей мало, и контейнер спрятал бы важное — что абстракции существуют и внедряются. Фабрика делает это явно. (Проговорить: «в продакшене DI-контейнер часто *заменяет* фабрику, но принцип тот же — конкретика в одном месте».)

### Шаг 3.3. Список того, что попадёт в код на этапе 3 (5 мин)

Зафиксировать как «домашнее задание → этап 3»:

- Интерфейсы: `IClock`, `IAccountNumberGenerator`, `IWithdrawalPolicy`, `IMonthEndRule`, `IStatementFormatter`, `IAccountOperations`, `IAccountStatement`.
- DTO: `WithdrawalDecision`.
- Реализации: `SystemClock`, `SequentialAccountNumberGenerator`, `StrictWithdrawalPolicy`, `OverdraftFeeWithdrawalPolicy`, три правила (`InterestOnPositiveBalanceRule`, `InterestOnNegativeBalanceRule`, `MonthlyDepositRule`), `TextStatementFormatter`.
- Переработанный `BankAccount`: хранит `List<Transaction>`, принимает 6 зависимостей в конструктор, реализует два интерфейса, `PerformMonthEndTransactions` — цикл по правилам.
- `AccountFactory` с тремя пресетами: `CreateInterestEarning`, `CreateLineOfCredit`, `CreateGiftCard`.

**Что НЕ попадает в этап 3:** удаление старых классов-наследников. Их оставляем в учебном репозитории как «до» — сравнение «до/после» нужно на защите. Удаление — по желанию, после сдачи.
